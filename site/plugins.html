Making plugins

A plugin is a JavaScript file that runs inside Notion's window. It can read the page, add a button, change how things look and behave, and offer options to the person using it.

Plugins have full access. A plugin can do anything Notion's own page can, including reading and changing every page you open. Notiskin does not sandbox plugin code. Only run plugins you wrote or trust, and write yours so anyone can read what it does.

Your first plugin

  1. Open Settings → Developer and turn on developer mode with a folder of your choice (see Developer mode). Or save the file as ~/.notiskin/plugins/hello.js and switch it on in the Plugins tab.
  2. Save this as hello.js in that folder: 
    notiskin.ready(() => {
  notiskin.addToolbarButton('Hello', () => {
    alert('You are on: ' + (notiskin.getPageTitle() || 'a page with no title'));
  });
});
  3. Notion reloads when you save, and a Hello button appears in the top bar.

The notiskin object

Plugins get window.notiskin, version 1.2.0 (it is in notiskin.version). In a plugin that declares settings, use the notiskin you are handed, see Settings. Every method below catches errors from your callbacks and logs them to Notion's console, so one broken callback doesn't stop the others.

MethodWhat it does
onPageChange(fn)Calls fn() when the page's address changes, which is when someone opens another page.
onBlockLoad(fn)Calls fn(content) with the page's content element (.notion-page-content) whenever the page changes while it is on screen. This runs often, on every change to the page, so keep it quick and don't change the page in a way that triggers it again.
getPageTitle()The current page's title as text, or null if there isn't one.
getPageUrl()The current address.
addToolbarButton(label, onClick)Adds a button to Notion's top bar and returns it. It uses Notion's colors, so it looks right in light and dark, and it is put back if Notion rebuilds the top bar. onClick gets the button. Returns null (and logs a warning) if the top bar isn't there yet, so call it inside ready or onPageChange.
removeToolbarButton(button)Removes a button that addToolbarButton returned, for good.
onContentChange(fn)Like onBlockLoad, but called at most four times a second. Use it for anything that reads the page. Returns a function that stops listening.
addStyle(id, css)Adds your CSS as a style element, or replaces it when the id is used again. Use your plugin's name in the id. Returns the element.
removeStyle(id)Removes a style that addStyle added.
getPageScroller()The element that scrolls the open page, or null. Use it for the scroll position.
getPageId()The open page's id (32 letters and numbers), or null.
getColorScheme()'dark' or 'light', following Notion's own setting.
onColorSchemeChange(fn)Calls fn('dark') or fn('light') when it changes. Returns a function that stops listening.
ready(fn)Calls fn() now if the page has finished loading, otherwise when it has.
settings.get(key), getAll(), onChange(fn)The options a plugin declares, see Settings.

Anything else is plain browser JavaScript: document.querySelector, MutationObserver, fetch and so on. Notion's page structure changes when Notion updates, so prefer .notion-* class names and check that what you looked for was found.

Watch your observers. A MutationObserver that changes the page it is watching will call itself forever and freeze Notion. Watch the smallest part of the page you can, wrap the callback in try/catch, and add a guard so it does nothing when it just ran.

Notion removes what is far from the screen. On a long page, blocks above and below the window are taken out of the page until you scroll back to them, so a plugin that reads the page's text only sees what is loaded. Use getPageScroller() for how far down the page is, which stays correct.

When a plugin runs

  • Once per page load, in every Notion tab and window. Changing the theme or a setting doesn't run it again, so listeners don't pile up.
  • When a plugin is turned off, deleted, or its developer file changes, Notion's tabs reload, because JavaScript that has run can't be taken back.
  • In safe mode nothing runs, and nothing is deleted. It all comes back when safe mode is turned off.
  • A plugin that throws while loading is logged and skipped. It doesn't stop other plugins.
  • A plugin that has no declared settings runs as plain top-level code: var and function at the top level become globals, and notiskin is window.notiskin.

Settings

A plugin can offer options. Declare them in a comment at the very top of the file, one line per setting, with @notiskin-setting followed by a JSON object:

/**
 * @notiskin-setting {"key":"compact","type":"toggle","label":"Compact sidebar","default":false}
 * @notiskin-setting {"key":"greeting","type":"text","label":"Greeting","default":"hello","maxLength":40}
 * @notiskin-setting {"key":"size","type":"number","label":"Size","default":14,"min":8,"max":32,"step":2}
 * @notiskin-setting {"key":"mode","type":"select","label":"Mode","default":"calm","options":["calm","loud"]}
 * @notiskin-setting {"key":"accent","type":"color","label":"Accent color","default":"#e8590c","description":"Optional text under the label"}
 */
if (notiskin.settings.get('compact')) {
  document.body.classList.add('my-compact');
}
notiskin.settings.onChange((key, value, all) => {
  if (key === 'compact') document.body.classList.toggle('my-compact', value);
});

The Plugins tab then shows a Settings button on the plugin's card with a form made from the lines, and what the person picks shows in Notion right away: no reload, and your onChange hears about it. The app reads the comment as text and never runs the plugin to do it, so the form works while the plugin is off.

typeValueOther fields
toggletrue or false
texttextmaxLength, 1 to 2000, 200 if you leave it out
numbera numbermin, max, step
selectone of optionsoptions: 1 to 20 texts, required
color#rrggbb

Every setting needs key (letters, numbers and underscores, starting with a letter, up to 40), label (up to 60 characters), type and a valid default. description is optional. You can declare up to 20. A line that isn't valid JSON, has an unknown type, a default that doesn't fit, or repeats a key is skipped, and the form says why. The rest still work. Only comments before the first line of code count.

Reading values

  • notiskin.settings.get(key) is what the person picked, or your default.
  • notiskin.settings.getAll() is a copy of all of them.
  • notiskin.settings.onChange(fn) calls fn(key, value, all) after a change, once for each key that changed, and returns a function that stops listening.

One thing that is different. So that settings knows which plugin is asking, even from a callback that runs later, a plugin that declares settings is run inside a function that is given its own notiskin. Use that notiskin, not window.notiskin, and don't count on top-level var and function becoming globals: write window.thing = ... when you mean a global. A plugin with no @notiskin-setting lines runs exactly as before.

Developer mode

To write a plugin without installing it each time, turn on Settings → Developer and pick a folder. Every .js file in it runs in Notion like an installed plugin, and saving a file reloads Notion's tabs so the new code runs. The files stay where they are, nothing is copied into ~/.notiskin/plugins.

  • They are listed on the Plugins tab under Developer plugins with a dev label. They are always on, and they never appear in Browse or Publish.
  • Only plain .js files count: a simple name (letters, numbers, spaces, dashes, dots and underscores), at most 512 KB each, at most 50 files. A link to a file, a folder called something.js, a file that is too big, or one with an odd name is skipped, and Settings says why.
  • Turning it on asks first, because the folder's files run with full access to Notion. Only choose a folder you control.
  • Safe mode pauses them and stops watching the folder. Turning developer mode off, or choosing another folder, reloads Notion's tabs too.
  • Look at Notion's console for your console.log output and errors. In Notion, press Cmd+Option+I.

Safety and review

Notiskin shows a warning the first time someone turns on any plugin, and nothing stops a plugin from doing what Notion's page can do. The marketplace's protection is that a person reads every plugin before it is listed, and again when a new version is published. These are the facts that are built into the app:

  • A published plugin is not live until a reviewer approves it. If the reviewer rejects it, the reason is shown in your Submissions.
  • A new version of a listed plugin is reviewed too. The reviewer sees the lines that changed, and the version people have stays live until the new one is approved. You can have one version waiting at a time.
  • A plugin can be reported. When three different accounts that are at least a day old report it as harmful it is hidden from Browse automatically, and reviewers can hide any item. People who installed it see a warning on the card and can turn it off. Nothing is turned off or deleted for them without their say.
  • Reviewers decide by reading the code. There isn't a longer rulebook. What makes a review quick: say what the plugin does in the description, keep the code readable (no minified or hidden code), don't load code from somewhere else, and don't send anything about the person's pages anywhere.

Publishing and versions

  1. Sign in with GitHub in Settings.
  2. Open Publish on the Plugins page. Give it a name (letters, numbers and spaces, up to 50), a description, up to 3 tags and optionally a link to a GitHub repository or gist. Paste the code, up to 200,000 characters. The @notiskin-setting lines are part of the code, so reviewers see them.
  3. It waits for a reviewer. Submissions shows where it is. You can publish 5 things per hour (themes and plugins together).
  4. After it is listed, Publish a new version takes the new code and a line about what changed. People who installed the plugin see an Update button, and updating a plugin asks them to read the warning and the change note first.
